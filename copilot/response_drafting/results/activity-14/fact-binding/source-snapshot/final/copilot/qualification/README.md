# Customer qualification

This module selects missing customer requirements after the enquiry workflow has chosen its route. It changes staff-facing questions while preserving the active clarification, pending reply, owner, next action and approvals.

- `contract.py` defines the versioned qualification context, fact identifiers and validated multi-group planner output. JSON Schemas are in `contracts/qualification`.
- `extraction.py` recognises explicit customer requirements with exact evidence spans before model planning. It keeps polarity local to each assertion, excludes uncertain or documentation-only claims, and requires route/request scope for stop counts.
- `facts.py` merges validated interpretation values and explicit customer requirements into the existing shared diagnostic state. Additional model-extracted facts require an exact customer excerpt and a literal or controlled-alias grounding check. Requirement excerpts are checked in their enclosing customer assertion so short quotes cannot hide negation or provider capabilities. Boolean values require field-specific evidence and explicit polarity; an omitted detail remains unknown. Boolean placeholders are rejected for non-Boolean requirements. Explicitly stated output languages are reused.
- `requirements.py` supplies applicable decision profiles from the API and customer task. Interpretation completeness metadata is not treated as a list of questions to ask.
- `planning.py` uses the shared model client to extract explicit facts and propose priorities within those profiles. The requirement catalogue fixes complete decision groups, while the model provides evidenced facts and priorities. Supplied, previously asked and declined fields are filtered before questions and shared state are published.
- `validation.py` validates the complete planner response. It can cap an overlong diagnostic reason or omit schema-invalid fact entries, then revalidate without another model call. Facts and question groups remain intact when only the reason is capped. Remaining errors allow one schema-repair request within the shared retry, token and deadline limits. Facts still require customer evidence before admission.
- `wording.py` renders one question for each independent decision group.
- `workload.py` checks monthly quantity usability and preserves the stated workload unit. Raw outlet counts, unbound numbers and non-monthly rates stay incomplete. Matrix operations remain distinct from elements, and session counts remain distinct from requests.

The context is available at `diagnostic_context.qualification`. Facts are also persisted through the existing `diagnostic_state`, so the same evidence and question lifecycle are available when a case is reopened. The existing interpretation input and output schemas remain compatible. Explicit service operating locations supply usage geography through the shared pricing-qualification extractor; billing country alone does not establish usage location.

Observed diagnostic failures continue through the diagnostic planner. Qualification planning supports multiple independent requirements, such as monthly workload, traffic needs, vehicle mode, session completion, deployment responsibility and storage rights. A pure documentation question can produce an empty qualification plan.

For example, an autocomplete quote can require separate confirmation of session completion and debouncing. If the customer already states that sessions end in Place Details Essentials, the terminating SKU is preserved as supplied and is not requested again.

Staff suggestions are not marked as asked until they become active through the existing case flow. Enriching an active question changes its staff presentation only; its original pending field and task remain unchanged. Validation attempts are recorded in `qualification_plan_validation` with response hashes and input-free field/type errors. If local recovery and the bounded repair cannot produce a valid plan, the active questions and pending reply are preserved. The deterministic pricing-eligibility path remains available when it is the only allowed diagnostic decision. Controlled customer-requirement templates use the requirement context of the question filter, so customer route-size requirements are not confused with provider service limits. Credential checks remain active.
